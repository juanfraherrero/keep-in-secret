Just git
Plain add, commit, push and pull. kis runs inside git as a filter, with no extra steps in your workflow.

      

      

        

        
Zero plaintext upstream
Your history and your remote only ever see authenticated AES-256-GCM ciphertext.

      

      

        

        
Share with a key
Add partners by age key, SSH key, or github:user. Revoking someone rotates the repository key.

      

      

        

        
Fails closed
No key? git add refuses, and a pre-commit check blocks any plaintext that slips through.

      

    

  







  

    

      
Get started

      
Three commands. That's the whole setup.

      
Install once per machine, like git-lfs. Nothing executable ever lives in the repository.

    

    

      

        01 · INSTALL
        
Everyone

        
You need git 2.28 or newer (check with git --version; kis tells you how to upgrade if it's older). The script installs the latest release for macOS or Linux, git kis included. On Windows, grab the zip from the releases, or use go install.

        
curl -fsSL https://raw.githubusercontent.com/juanfraherrero/keep-in-secret/main/install.sh | sh

      

      

        02 · OWNER
        
Encrypt the repo, add a partner

        
init creates .gitencrypt (.env, .env.*) and your key, and encrypts what matches.

        
kis init
kis add ana github:ana   # or age1… / ana.pub
git commit -m "Set up kis" && git push

      

      

        03 · PARTNER
        
Send a key, unlock

        
Make a key, send the public half to the owner, then unlock after cloning. An existing SSH key works too.

        
kis keygen        # prints age1… → send it
git clone … && cd …
kis unlock        # .env is now plaintext

      

    


    

      
kis initSet up encryption in the repo (--ssh to use your SSH key)

      
kis keygenCreate your personal age key and print the public key

      
kis add NAME KEYGive someone access: age1…, github:USER or FILE.pub

      
kis remove NAMERevoke access and rotate the master key

      
kis unlockDecrypt after cloning; wires up the git filters and hook

      
kis lockForget the key here and turn files back into ciphertext

      
kis rotateNew master key, re-encrypt everything

      
kis syncApply .gitencrypt edits to .gitattributes (--preset terraform and others for non-.env stacks)

      
kis status --checkIs it safe to push? Exits 1 if a secret would leave in plaintext; --json for agents, --since origin/main for PRs

      
kis pubkeyPrint the public keys found on this machine

How it works

      
Under the hood: git filters + SIV-style AEAD + age.

      
About 2,800 lines of Go, built on the standard library's crypto plus filippo.io/age. Here is every layer.

    


    

      
      

        
01
Git filters do the moving

          
.gitencrypt compiles into a managed block in .gitattributes (.env filter=kis diff=kis merge=kis), matching exactly what the same line in a .gitignore would. Git then pipes those files through kis whenever content crosses between the working tree and the object database.

02
Deterministic, authenticated encryption

            
Git compares content by hash, so the same plaintext must always give the same bytes. Otherwise every secret would show as modified forever. The nonce is therefore derived from the content.

          

            
master key · 32B→HKDF-SHA256→encKeymacKey

            
plaintext→HMAC(macKey)[:12]=nonce

            
AES-256-GCM(encKey, nonce, aad=Magic)→ciphertext ‖ tag

          

          
A nonce repeats only when the plaintext is identical, and then the output is identical too, so GCM's nonce-reuse problem never comes up. On decrypt, kis recomputes the HMAC and rejects the file unless it matches (hmac.Equal).

        


        
        

          
03
The blob format

            
Every encrypted file is self-describing. The leading NUL byte makes git treat it as binary, so it never prints a line diff of noise. textconv shows you the real diff when you're unlocked.

          

            
Magic8 bytes

            
nonce12 bytes

            
ciphertextn bytes

            
tag16 bytes

          

          

          
Encrypting is idempotent: content that already carries the header passes straight through the clean filter.

        

      


      
      

        
04
One repository key, one lockbox per partner

          
A random master key encrypts the files. That key is then encrypted with age for each partner's public key (X25519, or SSH ed25519/RSA) and committed, ASCII-armored. Only that partner's private key can open their box. kis unlock caches the master key in .git/kis/key, which is never committed.

        

          

            
master key32 random bytes

            

              
juan.ageage1qz8…x4k

              
ana.agessh-ed25519 AAAA…

              
leo.agegithub:leo → 2 keys

            

          


.kis/
├── config.toml      # default_key = "age" | "ssh"
├── recipients.toml  # name → [public keys]
└── keys/
    ├── juan.age     # master key, for juan
    └── ana.age      # master key, for ana
.git/kis/key         # local cache, 0600, never pushed

        

        
Revoke: kis remove ana generates a new master key, re-wraps it for everyone who's left, re-encrypts every secret (git add --renormalize) and deletes ana.age. Remaining partners pull and run kis unlock again.

      


      

        
        

          
05
One process, not one per file

            
kis speaks git's long-running filter process protocol (v2, pkt-line framing). Git starts it once per command and streams every file through it, and the key is loaded only once.

          

            
git →git-filter-client · version=2 · 0000

            
kis →git-filter-server · version=2 · 0000

            
git →capability=clean · capability=smudge · 0000

            
kis →capability=clean · capability=smudge · 0000

            
git →command=clean · pathname=.env · 0000 · <content> · 0000

            
kis →status=success · 0000 · \0KIS\0v1\0… · 0000

          

        


        
        

          
06
Fails closed, never loud

            
The rules are asymmetric on purpose: storing plaintext is never allowed, and reading without a key is never an error.

          

          

            
UnlockedLocked

            
              
clean · git addencryptrefuse: nothing staged

              
smudge · checkoutdecryptpass ciphertext through

              
merge · conflictsdecrypt, text merge, re-encryptrefuse: normal conflict

              
pre-commitblocks plaintext in staged secrets, or a stale .gitattributes

              
filter.requiredif kis crashes, git fails rather than storing plaintext

            
          

          

        

      


      
      

        
07
Threat model, honestly

        

          
    
            
  • No plaintext in git. Not in objects, history, or the remote.
    • 
            
  • Tamper-evident. GCM tag + nonce re-check reject modified blobs.
    • 
            
  • A clone without a key leaks nothing. You just get ciphertext.
    • 
          

          
    
            
  • Past commits. Whoever could unlock once can read old history. Rotate the real credentials after removing someone.
    • 
            
  • Metadata. File names, sizes, and when a secret changed are visible.
    • 
            
  • Endpoints. Secrets are only as safe as the least protected laptop holding a key.
